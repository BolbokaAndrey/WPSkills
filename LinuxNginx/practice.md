# Практика: Bitrix + PHP-FPM + Nginx

Готовый стенд находится в каталоге [`practice`](practice). Схема: внешний сервис `nginx` принимает HTTP/HTTPS, отдает статические файлы сам и проксирует динамику по `least_conn` в две реплики Nginx-бэкенда. Каждый бэкенд передает PHP в реплики PHP-FPM. MariaDB доступна только внутри Docker-сети.

```text
Клиент → nginx:443 → backend (2 реплики):8080 → fpm (2 реплики):9000 → MariaDB
                    └──────── статические файлы отдает сам ─────────┘
```

## Назначение контейнеров

| Контейнер | Для чего нужен |
|---|---|
| `nginx` | Внешняя точка входа. Принимает запросы клиента на `80`/`443`, делает HTTP → HTTPS редирект, завершает TLS, отдает статику и по `least_conn` проксирует динамические запросы на сервис `backend`. |
| `backend` (2 реплики) | Внутренние HTTP-узлы приложения. Каждая реплика получает запрос от `nginx`, применяет правила Bitrix URL rewrite и передает PHP-файлы сервису `fpm`. Реплики Docker автоматически обнаруживаются через DNS `127.0.0.11`. |
| `fpm` (2 реплики) | Процессы PHP-FPM, которые выполняют PHP-код Bitrix. HTTP они не принимают; реплики выбираются внутренним Nginx по `least_conn`. |
| `db` | MariaDB с данными Bitrix. Не публикуется наружу и доступна только контейнерам Docker-сети по имени `db`. |

`nginx` и `backend` — разные сервисы намеренно. Внешний `nginx` демонстрирует обратный прокси (`proxy_pass`) и балансирует два HTTP-узла `backend`; `backend` демонстрирует передачу PHP в FPM. Упрощенная схема `nginx` + две реплики `fpm` тоже возможна: внешний Nginx будет использовать `fastcgi_pass` напрямую. Но в ней не будет отдельного HTTP-бэкенда и балансировки через `proxy_pass`.

## 1. Установка Nginx

На Debian/Ubuntu при необходимости установить Nginx на хосте:

```bash
sudo apt update
sudo apt install -y nginx
nginx -v
```

В стенде ниже Nginx запускается в Docker-контейнерах, поэтому хостовый Nginx не должен занимать порты `80` и `443`.

## 2. Запуск стенда

```bash
cd practice
bash scripts/generate-cert.sh
docker compose up --build -d
docker compose ps
```

У сервисов `backend` и `fpm` указано `scale: 2`, поэтому Compose запускает по две реплики. Для изменения количества поменять это значение в `compose.yaml` и повторно выполнить `docker compose up -d`.

Рабочий хостнейм: `bitrix.172.16.11.34.nip.io`. Он резолвится в корпоративный IP `172.16.11.34`, поэтому запись в `/etc/hosts` не нужна. Другие поддомены закрываются сервером по умолчанию. Если `.nip.io` недоступен, добавить в `/etc/hosts` строку `172.16.11.34 bitrix.local` и заменить `server_name` и CN сертификата на `bitrix.local`.

Самоподписанный сертификат вызывает предупреждение браузера. Для проверки через curl использовать `-k`:

```bash
curl -I http://bitrix.172.16.11.34.nip.io
curl -kI https://bitrix.172.16.11.34.nip.io/redirect-me
curl -k --compressed https://bitrix.172.16.11.34.nip.io/app.js
```

Первый запрос возвращает `301` на HTTPS; `/redirect-me` — `302` на `/`. Файл `app.js` уже добавлен для проверки gzip: заголовок ответа будет `Content-Encoding: gzip` при передаче `--compressed`.

## 3. Bitrix и PHP-FPM

Две реплики `fpm` собраны с PHP 8.2 FPM и расширениями `mysqli`, `pdo_mysql`, `mbstring`, `gd`, `intl`, `zip`, `opcache`, нужными типовой установке Bitrix. Процесс PHP-FPM использует UID/GID `1000`, как владелец каталога `practice/app`, поэтому установщик Bitrix может записывать файлы. Файлы сессий PHP сохраняются в `/tmp`, доступный этому пользователю. Поместить дистрибутив Bitrix в `practice/app` и пройти штатный web-установщик по адресу:

```text
https://bitrix.172.16.11.34.nip.io/
```

Параметры базы в установщике:

```text
Сервер: db
База: db
Пользователь: db
Пароль: db
```

Текущие `index.php` и `api/node.php` — минимальные диагностические файлы. Их заменит дистрибутив Bitrix; `api/node.php` можно оставить для демонстрации балансировки.

## 4. Что реализовано в конфигурации

- Проксирование динамических запросов: `proxy_pass http://bitrix_backends`.
- Статика: regex-location в `nginx.conf` и `try_files $uri =404`.
- Редиректы: HTTP → HTTPS (`301`) и `/redirect-me` → `/` (`302`).
- Gzip для JavaScript: `gzip on` и `gzip_types application/javascript ...`.
- Балансировка минимум на двух HTTP-узлах: две реплики `backend`, DNS Docker и `upstream bitrix_backends` + `least_conn`.
- TLS: самоподписанный сертификат в `practice/certs`, который создает скрипт.
- Лимит загрузки: `client_max_body_size 100m`; таймауты прокси: 5/60/60 секунд.

## 5. Проверка балансировки и логов

Выполнить параллельные запросы, чтобы стратегия `least_conn` распределила активные соединения:

```bash
seq 1 20 | xargs -P 10 -I{} \
  curl -ks https://bitrix.172.16.11.34.nip.io/api/node.php

docker compose logs backend
```

В выводе запросов будут имена разных контейнеров; в логах будут префиксы `backend-1` и `backend-2`. Это подтверждает, что запросы действительно дошли до двух реплик.

Остановка стенда без удаления данных: `docker compose down`. Для удаления также тома MariaDB: `docker compose down -v`.
