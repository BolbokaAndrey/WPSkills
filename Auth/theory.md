# Авторизация и аутентификация

## Общие вопросы

### Что такое stateless/statefull авторизация

**Statefull (с хранением состояния)** — сервер сам хранит информацию о том, что пользователь авторизован (обычно в виде сессии в базе данных, Redis или памяти). Клиенту выдаётся только идентификатор сессии (session id), по которому сервер на каждый запрос ищет данные о пользователе. Плюсы: можно в любой момент принудительно завершить сессию (разлогинить пользователя), легко хранить много данных о сессии. Минусы: нужно хранилище состояния, сложнее масштабировать на несколько серверов (нужна общая база сессий или sticky-сессии).

**Stateless (без хранения состояния)** — сервер не хранит ничего о пользователе между запросами. Вся необходимая информация (id пользователя, роли, срок действия) зашита в сам токен (обычно JWT), который подписан сервером. Сервер только проверяет подпись токена и достаёт из него данные. Плюсы: легко масштабировать (любой сервер в кластере может проверить токен, не обращаясь к общей базе), не нужно хранилище сессий. Минусы: сложно досрочно отозвать токен (он валиден до истечения срока, если не завести отдельный механизм отзыва — чёрный список и т.п.).

### Что такое basic авторизация

Basic-авторизация (HTTP Basic Authentication) — простейший способ передачи логина и пароля в HTTP-запросе. Логин и пароль склеиваются через двоеточие (`login:password`), кодируются в Base64 и передаются в заголовке:

```
Authorization: Basic bG9naW46cGFzc3dvcmQ=
```

Важно: Base64 — это не шифрование, а просто кодирование, поэтому логин и пароль легко восстановить из заголовка. Basic-авторизацию можно использовать только поверх HTTPS, иначе учётные данные передаются фактически в открытом виде. Обычно применяется для простых внутренних сервисов, служебных API или защиты тестовых окружений — для полноценных приложений с пользователями не подходит.

### Что такое авторизация и аутентификация

Это два разных, но часто путаемых понятия:

- **Аутентификация (authentication)** — проверка того, что пользователь действительно тот, за кого себя выдаёт. Отвечает на вопрос «кто ты?». Пример: ввод логина и пароля, вход по коду из SMS, вход через Google.
- **Авторизация (authorization)** — проверка прав пользователя на конкретное действие или ресурс. Отвечает на вопрос «что тебе можно?». Пример: проверка, может ли пользователь редактировать чужой заказ, или доступна ли ему админ-панель.

Аутентификация всегда происходит раньше авторизации: сначала система понимает, кто перед ней, потом решает, что этому пользователю разрешено.

### Что такое сессии? Какой у них принцип работы? Нужны ли cookie для работы сессий?

Сессия — это способ сохранить состояние пользователя (то, что он залогинен, и его данные) на стороне сервера между отдельными HTTP-запросами, которые сами по себе не имеют памяти (протокол HTTP не хранит состояние).

Принцип работы:
1. Пользователь логинится (отправляет логин/пароль).
2. Сервер проверяет данные, создаёт запись сессии (в памяти, Redis, базе данных) с уникальным идентификатором и связанными данными пользователя.
3. Сервер отдаёт клиенту этот идентификатор сессии.
4. При каждом следующем запросе клиент отправляет этот идентификатор, сервер находит по нему сессию в хранилище и понимает, кто делает запрос.

Cookie — самый распространённый, но не единственный способ хранить и передавать идентификатор сессии. Cookie удобны тем, что браузер сам автоматически прикрепляет их к каждому запросу на нужный домен. Но идентификатор сессии можно передавать и иначе — например, в заголовке `Authorization`, в query-параметре URL (менее безопасно) или через localStorage с ручной отправкой в заголовке. Поэтому cookie не являются обязательным условием работы сессий — это лишь самый удобный транспорт для веб-браузеров.

### Какие способы защиты cookie?

- **HttpOnly** — запрещает доступ к cookie из JavaScript (`document.cookie`), защищает от кражи cookie через XSS-атаки.
- **Secure** — cookie передаётся только по HTTPS-соединению, не отправляется по обычному HTTP.
- **SameSite** — ограничивает отправку cookie при кросс-доменных запросах, защищает от CSRF-атак. Значения:
  - `Strict` — cookie не отправляется вообще при переходе с другого сайта.
  - `Lax` — cookie отправляется только при безопасных переходах (например, обычный переход по ссылке), но не при отправке форм или AJAX-запросах с другого домена.
  - `None` — cookie отправляется всегда, но обязательно требует флаг `Secure`.
- **Ограничение срока жизни (Expires/Max-Age)** — чем короче срок жизни, тем меньше окно для злоупотребления украденной cookie.
- **Ограничение домена и пути (Domain, Path)** — cookie должна выдаваться максимально узко, только на нужный домен/путь, чтобы не утекать на поддомены или другие разделы сайта.
- **Подпись/шифрование значения cookie** — чтобы пользователь не мог подделать или изменить содержимое cookie на клиенте.
- **Регенерация id сессии после логина** — защита от session fixation (когда злоумышленник заранее подсовывает жертве известный ему id сессии).

### Что такое OAuth?

OAuth (точнее, актуальная версия — OAuth 2.0) — это протокол **авторизации**, а не аутентификации. Он позволяет одному приложению получить ограниченный доступ к ресурсам пользователя на другом сервисе, не получая при этом его логин и пароль напрямую.

Классический пример: приложение хочет получить доступ к списку контактов пользователя в Google. Вместо того чтобы просить пароль от аккаунта Google, приложение перенаправляет пользователя на страницу авторизации Google, пользователь там подтверждает доступ, и Google выдаёт приложению временный access token с ограниченными правами (только на чтение контактов, например). Приложение никогда не видит пароль пользователя.

Ключевые участники OAuth:
- **Resource Owner** — сам пользователь.
- **Client** — приложение, которое хочет получить доступ.
- **Authorization Server** — сервер, который аутентифицирует пользователя и выдаёт токены.
- **Resource Server** — сервер, где хранятся данные (API), к которым получаем доступ.

Важно: сам по себе OAuth не отвечает на вопрос «кто этот пользователь» — он лишь выдаёт токен доступа к ресурсу. Для аутентификации поверх OAuth используется отдельное расширение — OIDC (см. ниже).

#### Как работает Authorization Code Flow

Это основной и самый безопасный поток OAuth 2.0 для приложений, у которых есть серверная часть (back-end), способная хранить секрет. Ключевая идея: токен никогда не проходит через браузер — через браузер передаётся только одноразовый код, который бесполезен без секрета приложения.

Шаги:

1. **Запрос авторизации.** Пользователь нажимает «Войти через ...». Приложение перенаправляет браузер на страницу сервера авторизации с параметрами:
   ```
   GET /authorize?response_type=code
                 &client_id=ID_ПРИЛОЖЕНИЯ
                 &redirect_uri=https://app.example.com/callback
                 &scope=read_contacts
                 &state=СЛУЧАЙНАЯ_СТРОКА
   ```
   - `client_id` — идентификатор приложения, зарегистрированного на сервере авторизации;
   - `redirect_uri` — куда вернуть пользователя после подтверждения (должен точно совпадать с заранее зарегистрированным);
   - `scope` — запрашиваемые права;
   - `state` — случайное значение, которое приложение запоминает; защищает от CSRF-атаки на процесс входа.
2. **Аутентификация и согласие.** Сервер авторизации проверяет, кто пользователь (просит войти, если он ещё не вошёл), и показывает экран: «Приложение X запрашивает доступ к ...». Пользователь подтверждает.
3. **Выдача кода.** Сервер авторизации перенаправляет браузер обратно на `redirect_uri`, добавляя одноразовый **authorization code** (короткоживущий, обычно до нескольких минут) и тот же `state`:
   ```
   https://app.example.com/callback?code=ОДНОРАЗОВЫЙ_КОД&state=СЛУЧАЙНАЯ_СТРОКА
   ```
   Приложение сверяет `state` с сохранённым — если не совпадает, запрос отклоняется.
4. **Обмен кода на токены.** Back-end приложения напрямую (не через браузер) отправляет запрос на сервер авторизации:
   ```
   POST /token
   grant_type=authorization_code
   &code=ОДНОРАЗОВЫЙ_КОД
   &redirect_uri=https://app.example.com/callback
   &client_id=ID_ПРИЛОЖЕНИЯ
   &client_secret=СЕКРЕТ_ПРИЛОЖЕНИЯ
   ```
   Здесь используется `client_secret`, известный только приложению и серверу авторизации, — поэтому перехваченный код сам по себе бесполезен.
5. **Получение токенов.** Сервер авторизации проверяет код и секрет и возвращает `access token` (доступ к API), при необходимости `refresh token` (для получения нового access token) и, если используется OIDC, `id token`. Код после использования становится недействительным.
6. **Обращение к ресурсу.** Приложение вызывает API ресурсного сервера, передавая `Authorization: Bearer <access token>`. Ресурсный сервер проверяет токен и отдаёт данные в пределах выданных прав (`scope`).

**Authorization Code + PKCE.** Для приложений, которые не могут хранить секрет (SPA, мобильные приложения), используется то же самое, но вместо `client_secret` применяется PKCE (Proof Key for Code Exchange, произносится «пикси»):
- на шаге 1 приложение генерирует случайную строку `code_verifier`, считает от неё хеш `code_challenge` и отправляет его в запросе авторизации;
- на шаге 4 вместе с кодом отправляет исходный `code_verifier`;
- сервер авторизации хеширует его и сравнивает с полученным ранее `code_challenge`.

Так даже перехваченный код нельзя обменять на токен: у злоумышленника нет `code_verifier`. Сегодня PKCE рекомендуется использовать во всех случаях, в том числе для приложений с back-end.

### Что такое Implicit аутентификация?

Implicit Flow (неявный поток) — один из типов авторизационных потоков (grant types) в OAuth 2.0/OIDC, предназначенный изначально для одностраничных приложений (SPA), которые работают полностью в браузере и не имеют защищённого back-end, способного хранить секрет клиента.

Отличие от стандартного Authorization Code Flow: в Implicit Flow токен (access token, а при использовании OIDC — ещё и id token) возвращается сразу в URL фрагменте (после `#`) после редиректа с сервера авторизации, без промежуточного шага обмена авторизационного кода на токен через back-end. Это упрощает поток, но и снижает безопасность: токен проходит через адресную строку браузера, может попасть в историю браузера, логи прокси-серверов, а также отсутствует возможность использовать refresh token.

На сегодняшний день Implicit Flow считается устаревшим и не рекомендуется к использованию (это прямо прописано в актуальных рекомендациях OAuth 2.0 Security Best Practices). Вместо него для SPA рекомендуют Authorization Code Flow с расширением PKCE (Proof Key for Code Exchange), которое защищает от перехвата авторизационного кода без необходимости хранить секрет на клиенте.

### Что такое и зачем нужен OIDC?

OIDC (OpenID Connect) — это надстройка над OAuth 2.0, которая добавляет полноценную **аутентификацию**. Сам OAuth отвечает только за выдачу прав доступа (авторизацию), но не гарантирует и формально не подтверждает личность пользователя.

OIDC добавляет:
- **ID Token** — отдельный токен в формате JWT, который содержит проверяемую информацию о личности пользователя (id, email, имя и т.д.) и подписан сервером авторизации.
- Стандартизированный способ получить профиль пользователя (endpoint `/userinfo`).
- Чёткую спецификацию того, как проверять подлинность пользователя, а не только выдавать доступ к ресурсам.

Проще говоря: OAuth отвечает на вопрос «что этому приложению разрешено делать от имени пользователя», а OIDC поверх него отвечает на вопрос «кто именно этот пользователь». Именно OIDC используется в кнопках «Войти через Google/Apple/VK» — там нужна не только выдача доступа к API, но и подтверждение личности для входа в систему.

### Что такое SSO?

SSO (Single Sign-On, единый вход) — это подход, при котором пользователь один раз аутентифицируется в одной системе (например, в корпоративном портале или identity-провайдере) и после этого получает доступ ко всем связанным сервисам без повторного ввода логина и пароля.

Принцип работы: есть centralized Identity Provider (IdP), который хранит учётные записи и проверяет подлинность пользователя. Остальные приложения (Service Provider, SP) не хранят пароли сами, а доверяют IdP: при заходе пользователя в приложение оно перенаправляет его на IdP; если пользователь уже аутентифицирован там (есть активная сессия), IdP сразу возвращает подтверждение личности без повторного ввода пароля.

SSO реализуется на основе разных протоколов — чаще всего SAML (в корпоративной среде) или OIDC/OAuth 2.0 (в современных веб- и мобильных приложениях).

### Что такое SAML?

SAML (Security Assertion Markup Language) — это XML-based протокол для обмена данными об аутентификации и авторизации между Identity Provider и Service Provider, широко используемый для реализации SSO в корпоративных и enterprise-системах.

Принцип работы похож на OIDC, но старше и основан на XML вместо JSON: пользователь заходит в приложение (SP), оно перенаправляет его на IdP, IdP аутентифицирует пользователя и отправляет обратно в SP подписанный XML-документ — SAML Assertion, который подтверждает личность пользователя и, возможно, его атрибуты (роль, отдел, права).

SAML активно используется в корпоративной среде (интеграция с Active Directory, вход в различные корпоративные веб-сервисы через одну учётную запись), тогда как OIDC чаще применяется в современных вебе и мобильных приложениях благодаря более лёгкому формату (JSON) и лучшей поддержке в SPA/мобильных SDK.

### Что такое ActiveDirectory и LDAP?

**LDAP (Lightweight Directory Access Protocol)** — это протокол для доступа к иерархически организованным каталогам данных (directory services), чаще всего используемый для хранения информации о пользователях, группах, компьютерах в организации и их атрибутах (email, отдел, должность и т.д.). LDAP определяет, как клиенты могут искать, читать и изменять записи в таком каталоге.

**Active Directory (AD)** — это конкретная реализация службы каталогов от Microsoft, которая среди прочего поддерживает LDAP как один из протоколов доступа к своим данным. AD используется в первую очередь в корпоративной среде на базе Windows для централизованного управления учётными записями пользователей, компьютерами, группами и политиками безопасности в рамках одного домена или леса доменов.

Соотношение простыми словами: LDAP — это протокол (язык общения), Active Directory — это конкретный продукт (каталог), который этот протокол умеет обслуживать наряду с другими своими механизмами (Kerberos для аутентификации, например).

## JWT

### Что такое JWT токены и чем они отличаются от обычных токенов?

JWT (JSON Web Token) — это стандартизированный (RFC 7519) формат токена, который представляет собой самодостаточную структуру: внутри самого токена уже закодирована и подписана вся нужная информация (claims) — например, id пользователя, его роли, срок действия токена. Токен подписывается секретным ключом или парой ключей (публичный/приватный), и сервер может проверить подлинность токена, просто проверив подпись, без обращения к базе данных.

Отличие от «обычного» непрозрачного токена (opaque token, например обычный session id): opaque-токен — это просто случайная строка-идентификатор, которая сама по себе ничего не значит, и сервер обязан каждый раз идти в хранилище (базу, Redis), чтобы понять, кому этот токен принадлежит и какие у него права. JWT же может быть проверен локально на любом сервере (по подписи), без централизованного хранилища — это его главное преимущество для stateless-архитектур и микросервисов, но одновременно и источник сложностей с отзывом токена (см. ниже про уязвимости).

### Зачем нужен refresh token? Обязательно ли его использовать с JWT авторизацией?

Access token обычно делают недолгоживущим (минуты — часы), чтобы снизить ущерб от его утечки: если токен украли, он быстро станет бесполезным. Но постоянно заставлять пользователя логиниться заново — плохой UX. Refresh token решает эту проблему: это отдельный, обычно более долгоживущий токен, который хранится более защищённо (например, в httpOnly cookie) и используется только для одной цели — получить новый access token, когда старый истёк, без повторного ввода логина и пароля.

Refresh token не обязателен — можно обойтись только access token, особенно если он и так живёт долго или если приложение допускает частые повторные входы. Но в большинстве серьёзных систем связка access + refresh token — стандартная практика, так как позволяет одновременно держать access token коротким (безопасность) и не мучить пользователя частыми релогинами (удобство). Refresh token также обычно можно централизованно отозвать (хранится в базе), что частично решает проблему невозможности отзыва обычного JWT.

### Какая оптимальная длина жизни токена?

Единого универсального числа нет, всё зависит от чувствительности данных и модели угроз, но есть общепринятые ориентиры:

- **Access token**: от 5–15 минут до 1 часа для систем с повышенными требованиями к безопасности (банкинг, платежи); для обычных веб-приложений часто допустимо 15 минут — 1 час.
- **Refresh token**: от нескольких дней до нескольких недель. Часто применяют «скользящее» продление (rotation) — при каждом использовании refresh token выдаётся новый, а старый инвалидируется, что также помогает обнаружить кражу токена (если старый уже использованный refresh token снова пытаются применить — это признак компрометации).

Общий принцип: чем чувствительнее операция или данные, тем короче должен быть срок жизни access token, и тем строже должны быть механизмы обнаружения и отзыва при компрометации refresh token.

### Какие есть способы передачи токена от клиента? Что не так с cookie?

Основные способы:
1. **Заголовок Authorization** — `Authorization: Bearer <token>`. Самый распространённый способ для API. Токен хранится на клиенте (localStorage/sessionStorage/памяти приложения) и вручную добавляется в каждый запрос.
2. **Cookie** — токен передаётся автоматически браузером с каждым запросом на нужный домен.
3. **Query-параметр URL** — токен прямо в адресе запроса. Практически не рекомендуется: токен попадает в логи серверов, историю браузера, заголовок Referer.
4. **Тело запроса** — иногда используется для одноразовой передачи (например, при обмене refresh token на access token), но не годится для постоянной передачи с каждым GET-запросом.

Проблемы с cookie для хранения JWT:
- **CSRF (Cross-Site Request Forgery)** — если cookie отправляется автоматически браузером на любой запрос к домену, злоумышленник может заставить браузер жертвы отправить запрос от её имени с другого сайта. Требует дополнительной защиты (SameSite, CSRF-токены).
- **Ограничение по размеру** — у cookie обычно лимит около 4 КБ, JWT с большим количеством claims может туда не влезть.
- **Автоматическая отправка на все запросы к домену**, включая те, где токен не нужен, что увеличивает объём трафика и площадь атаки.
- При этом cookie с флагом HttpOnly недоступна для JavaScript, что, наоборот, хорошо защищает от XSS — поэтому у cookie есть и плюсы, просто требуется явно закрывать CSRF-риск (в отличие от заголовка Authorization, где токен в JS-памяти уязвим для XSS, но не для CSRF).

### Из чего состоит jwt токен?

JWT состоит из трёх частей, разделённых точками, каждая закодирована в Base64Url: `header.payload.signature`

1. **Header (заголовок)** — JSON-объект с метаданными: алгоритм подписи (`alg`, например HS256 или RS256) и тип токена (`typ: JWT`).
2. **Payload (полезная нагрузка)** — JSON-объект с claims (утверждениями) — данными о пользователе и самом токене. Бывают:
   - зарегистрированные claims (стандартные, например `iss` — издатель, `exp` — время истечения, `sub` — subject/id пользователя, `iat` — время выпуска);
   - публичные и приватные (произвольные) claims — любые данные, которые нужны конкретному приложению.
3. **Signature (подпись)** — результат подписи первых двух частей секретным ключом (симметричным, например HMAC) или приватным ключом (асимметричным, например RSA/ECDSA). Позволяет проверить, что токен не был изменён после выпуска.

Важный момент: payload лишь закодирован в Base64, а не зашифрован — любой может декодировать и прочитать его содержимое. Поэтому в обычный JWT нельзя класть секретные данные (пароли и т.п.), если только это не JWE (см. ниже).

### Что такое JWE и JWS

Оба термина описывают разные способы защиты содержимого JWT:

- **JWS (JSON Web Signature)** — токен, который **подписан**, но не зашифрован. Это и есть «обычный» JWT в привычном понимании — его содержимое (payload) можно свободно прочитать, декодировав Base64, но нельзя незаметно изменить, потому что подпись это выдаст при проверке.
- **JWE (JSON Web Encryption)** — токен, содержимое которого **зашифровано**, а не просто подписано. Прочитать payload может только тот, у кого есть ключ расшифровки. Используется, когда в токене передаются действительно чувствительные данные, которые не должны быть доступны никому, кроме получателя.

**Из чего состоит JWE.** В отличие от JWS (три части), JWE состоит из **пяти** частей, разделённых точками, каждая закодирована в Base64Url:

```
header.encrypted_key.iv.ciphertext.tag
```

1. **Header (заголовок)** — JSON с параметрами шифрования: `alg` — способ защиты ключа шифрования содержимого (например, `RSA-OAEP`, `A256KW`), `enc` — алгоритм шифрования самого содержимого (например, `A256GCM`). Заголовок не зашифрован, но участвует в проверке целостности.
2. **Encrypted Key (зашифрованный ключ)** — одноразовый ключ (CEK, Content Encryption Key), которым зашифровано содержимое. Сам он зашифрован ключом получателя (например, его публичным ключом RSA), поэтому расшифровать его может только получатель. При прямом использовании общего ключа (`alg: dir`) эта часть пустая.
3. **Initialization Vector, IV (вектор инициализации)** — случайное значение, которое делает шифрование одних и тех же данных каждый раз разным.
4. **Ciphertext (шифротекст)** — зашифрованный payload (те же claims, что и в обычном JWT).
5. **Authentication Tag (тег аутентификации)** — контрольное значение, по которому получатель проверяет, что шифротекст и заголовок не были изменены. Он заменяет подпись: шифрование с проверкой целостности (AEAD, например AES-GCM) защищает данные и от чтения, и от подмены.

Как это работает: отправитель генерирует одноразовый ключ, шифрует им payload, шифрует сам ключ открытым ключом получателя и собирает все пять частей в токен. Получатель расшифровывает ключ своим закрытым ключом, затем расшифровывает и проверяет содержимое.

Если нужна и конфиденциальность, и подпись, токен сначала подписывают (JWS), а затем шифруют получившуюся строку (JWE) — получается вложенный JWT.

На практике в большинстве приложений используется именно JWS (обычный подписанный JWT), а JWE применяется реже — в основном там, где сам токен передаётся через недоверенные промежуточные звенья и его содержимое должно оставаться приватным даже от них.

### Когда стоит использовать JWT, а когда нет?

**Стоит использовать, когда:**
- Нужна stateless-архитектура — например, микросервисы, где разные сервисы должны независимо проверять токен без обращения к общей базе сессий.
- Есть необходимость передавать токен между разными доменами/сервисами (например, разными поддоменами или партнёрскими API).
- Нужно закодировать в токене доп. информацию (роли, права), чтобы не делать лишний запрос в базу на каждый запрос.
- Приложение и так использует OAuth 2.0/OIDC — там JWT естественный формат.

**Не стоит использовать (или стоит использовать с осторожностью), когда:**
- Нужен мгновенный и гарантированный отзыв доступа (например, для банковских операций или систем с высокими требованиями к немедленной блокировке пользователя) — JWT по своей природе живёт до истечения срока, отзыв требует дополнительного механизма (чёрный список, короткий TTL + refresh).
- Простое монолитное приложение с одной базой данных, где сессии прекрасно работают, не создавая лишней сложности — JWT здесь просто усложнение без реальной выгоды.
- Токен должен часто меняться в размере или содержать много данных — JWT увеличивает объём каждого запроса, так как передаётся целиком при каждом обращении.

### Где на фронте хранить JWT токен?

Основные варианты и их компромиссы:

- **In-memory (переменная в JS, состояние приложения)** — самый безопасный вариант с точки зрения XSS, так как токен не сохраняется физически и исчезает при перезагрузке страницы. Недостаток — пользователю придётся логиниться заново при каждом обновлении страницы (если не сочетать с refresh token в httpOnly cookie для восстановления сессии).
- **httpOnly cookie** — токен недоступен для JavaScript, что хорошо защищает от XSS. Но нужно закрывать CSRF (SameSite, CSRF-токены). Часто именно так хранят refresh token.
- **localStorage** — доступен между вкладками и переживает перезагрузку страницы, но полностью доступен через JavaScript, а значит уязвим для XSS: любой внедрённый скрипт может украсть токен.
- **sessionStorage** — то же самое, что localStorage, но привязан к вкладке и исчезает при её закрытии; уязвимости к XSS такие же.

Рекомендуемая практика для большинства веб-приложений: access token держать в памяти приложения (in-memory), а refresh token — в httpOnly + Secure + SameSite cookie. Это сочетает защиту от XSS (для refresh token) и минимизирует урон, если access token всё же утечёт (он быстро истекает).

### Как фронт может получить доступ к JWT токену?

Если токен хранится в памяти приложения, localStorage или sessionStorage — фронт имеет прямой доступ через обычный JavaScript-код (`localStorage.getItem(...)`, переменная состояния и т.д.), полученный, например, из ответа сервера при логине.

Если токен хранится в httpOnly cookie, то напрямую через `document.cookie` доступа нет — и это сделано намеренно, ради защиты от XSS. В этом случае фронту сам токен обычно и не нужен: браузер автоматически прикладывает cookie к каждому запросу на сервер, а фронту достаточно знать сам факт того, что пользователь авторизован (это можно получить отдельным API-запросом, например `/me`, который вернёт данные пользователя, если cookie валидна).

### Какие распространённые уязвимости с JWT ты знаешь? (OWASP JWT)

- **`alg: none`** — некоторые библиотеки позволяют указать в заголовке токена алгоритм `none`, что означает отсутствие подписи. Если сервер не проверяет это явно, злоумышленник может отправить токен без подписи с произвольным содержимым, и сервер его примет.
- **Подмена алгоритма подписи (алгоритмическая путаница, alg confusion)** — например, атака, при которой токен, подписанный асимметрично (RS256, приватным ключом), подделывается под симметричный (HS256), используя публичный ключ сервера как секрет для HMAC-подписи. Если сервер не жёстко проверяет ожидаемый алгоритм, такая подделка пройдёт проверку.
- **Слабый секретный ключ** — если секрет для HMAC-подписи короткий или предсказуемый, его можно подобрать брутфорсом и подделывать любые токены.
- **Хранение чувствительных данных в payload** — так как payload не зашифрован, а лишь закодирован, туда нельзя класть пароли, персональные данные и другую конфиденциальную информацию — их легко прочитать.
- **Отсутствие проверки срока действия (`exp`) или отсутствие ревокации** — токен может использоваться неограниченно долго, если сервер не проверяет `exp` или не имеет механизма отзыва (например, при компрометации или логауте).
- **Кража токена через XSS** — если токен хранится в localStorage/sessionStorage, украденный через XSS-скрипт токен можно использовать от имени пользователя до истечения срока действия.
- **Replay-атаки** — повторное использование перехваченного валидного токена злоумышленником, если нет привязки токена к дополнительным факторам (например, к устройству/IP) или короткого TTL.
- **Слишком долгий срок жизни токена без возможности отзыва** — увеличивает окно для эксплуатации при компрометации.

Рекомендации по защите: всегда явно указывать ожидаемый алгоритм на сервере при проверке (не доверять `alg` из самого токена), использовать длинные случайные секреты или асимметричные ключи, короткий TTL для access token, не хранить чувствительные данные в payload, использовать HTTPS повсеместно, реализовывать механизм отзыва для критичных случаев.

### Есть ли ограничения на размер JWT токена?

Строгого ограничения в самой спецификации JWT нет, но на практике есть косвенные ограничения:

- Если токен передаётся в заголовке `Authorization`, действуют ограничения на максимальный размер HTTP-заголовков, которые устанавливают веб-серверы и прокси (обычно порядка 8 КБ суммарно на все заголовки, конкретное значение зависит от настроек Nginx/Apache/балансировщика).
- Если токен передаётся через cookie, действует более жёсткое ограничение — как правило, около 4 КБ на одну cookie (и общий лимит на все cookie домена).
- Чисто практически: чем больше claims (данных) кладётся в payload, тем больше становится токен, и он передаётся целиком при каждом запросе, что увеличивает трафик — поэтому в payload рекомендуется класть только необходимый минимум данных (id пользователя, роли), а не весь профиль целиком.

### Как может помочь Gogatekeeper?

Gogatekeeper (ранее known as Keycloak Gatekeeper) — это прокси-сервис (reverse proxy), который берёт на себя всю логику аутентификации и авторизации через OAuth 2.0/OIDC перед защищаемым приложением, избавляя само приложение от необходимости реализовывать эту логику самостоятельно.

Как это помогает на практике: Gatekeeper ставится перед реальным сервисом (как sidecar или отдельный прокси) и перехватывает входящие запросы. Он сам проверяет наличие и валидность токена (JWT), при необходимости перенаправляет пользователя на страницу логина identity-провайдера (например, Keycloak), обновляет токены по мере истечения срока действия, добавляет нужные заголовки с данными пользователя перед проксированием запроса на настоящий backend. Таким образом сам защищаемый сервис вообще не занимается вопросами OAuth/OIDC и проверки токенов — он получает уже аутентифицированный запрос с готовыми данными о пользователе.

Это особенно удобно в микросервисной архитектуре: не нужно встраивать одну и ту же логику проверки токена в каждый сервис — достаточно поставить Gatekeeper перед каждым (или использовать общий edge-прокси/service mesh с аналогичной функцией), и вся логика безопасности централизуется в одном месте.

## Примеры

### Создаёшь с нуля интернет магазин с личным кабинетом, какой тип авторизации для него стоит выбрать и почему?

Для классического интернет-магазина с личным кабинетом оптимальный вариант — **сессии на основе cookie (statefull-подход)**, либо связка **access + refresh JWT-токенов**, если заранее понятно, что система будет расти в сторону нескольких клиентов (веб, мобильное приложение, партнёрские API).

Обоснование:
- Магазин, скорее всего, изначально работает как монолит или небольшой набор сервисов с общей базой данных — в этом случае классические серверные сессии просты в реализации, дают возможность мгновенно разлогинить пользователя (например, при подозрении на взлом аккаунта или смене пароля), не требуют продумывания механизма отзыва токенов.
- Для личного кабинета важна возможность оперативно отозвать доступ (заблокировать аккаунт, разлогинить на всех устройствах при смене пароля) — с сессиями это делается тривиально (удалить запись из хранилища сессий), с чистым JWT — сложнее.
- Если магазин с самого начала планируется как мобильное приложение + веб + отдельные API для партнёров, тогда более гибким выбором станет JWT (access + refresh token), так как он проще переносится между разными клиентами и не требует общего хранилища сессий при масштабировании на несколько серверов.
- Для входа можно дополнительно подключить OAuth/OIDC («Войти через Google/VK/Apple») как дополнительный, а не единственный способ входа — это улучшает конверсию регистрации, но основной механизм авторизации в личном кабинете (сессия или JWT) остаётся тем же.

Дополнительно обязательно: HTTPS везде, защита cookie (HttpOnly, Secure, SameSite), защита от брутфорса пароля, двухфакторная аутентификация как опция для пользователя.

### Ты создаёшь микросервисную архитектуру, какой тип авторизации лучше выбрать и почему?

Для микросервисной архитектуры оптимальный выбор — **stateless-авторизация на основе JWT**, обычно в связке с OAuth 2.0/OIDC и отдельным identity-провайдером (например, Keycloak, Auth0).

Обоснование:
- В микросервисах много независимых сервисов, которые могут масштабироваться и разворачиваться отдельно. Если использовать классические сессии, каждому сервису пришлось бы обращаться к общему централизованному хранилищу сессий при каждом запросе — это создаёт дополнительную точку отказа, увеличивает задержки и усложняет масштабирование.
- JWT позволяет каждому сервису **самостоятельно и локально** проверить подлинность запроса (по подписи токена), не обращаясь никуда за подтверждением — это критично для производительности и отказоустойчивости распределённой системы.
- Единый identity-провайдер (через OIDC) выдаёт токены один раз, а все сервисы просто доверяют его подписи — не нужно реализовывать логику аутентификации в каждом сервисе отдельно.
- Удобно комбинировать с прокси-решениями наподобие Gogatekeeper или API Gateway, которые берут на себя проверку токена перед сервисами, разгружая сами бизнес-сервисы от этой ответственности.

Момент, который обязательно нужно продумать заранее: проблема отзыва токена в stateless-модели. Решается коротким TTL access token (минуты) в сочетании с refresh token, который можно централизованно отозвать через identity-провайдер, плюс при необходимости — механизм чёрного списка (blacklist) для критичных случаев экстренной блокировки токена до истечения его срока.
